# Requirements Document

## Introduction

The Aruba Voucher Backend is a secure guest WiFi access management system that integrates with an Aruba AP-505 running InstantOS 8.11.2.0. It enables guest users to authenticate onto a wireless network by entering a unique, time-limited voucher code on an existing external captive portal hosted on GitHub Pages.

The system follows the verified Aruba InstantOS 8.11 external captive portal authentication flow: the Aruba AP intercepts guest HTTP traffic and redirects users to the captive portal, where they enter a voucher code. The portal submits credentials to `securelogin.arubanetworks.com/swarm.cgi`, which triggers a RADIUS Access-Request to FreeRADIUS. FreeRADIUS validates the code against the backend (via REST or direct database query) and returns Access-Accept or Access-Reject to grant or deny internet access.

The backend is built with Python FastAPI, backed by PostgreSQL, and is intended for development on a Windows machine with eventual deployment to a Linux VPS.

---

## Glossary

- **AP**: Aruba AP-505 access point running InstantOS 8.11.2.0.
- **Admin**: An authenticated system administrator who manages vouchers via the Admin Interface.
- **Admin_Interface**: The web-based management UI served by the FastAPI application, protected by admin credentials.
- **Aruba_Redirect**: The HTTP 302 redirect issued by the AP when a guest connects, which includes query parameters: `mac`, `essid`, `ip`, `apname`, `apmac`, `url`, and `switchip`.
- **Captive_Portal**: The guest WiFi landing page hosted on GitHub Pages at `https://christianricv-tech.github.io/WIFI-Guest/`. Its source is maintained in `captive-portal/` in this repo and submits voucher codes to the Aruba `swarm.cgi` authentication endpoint (it validates nothing itself and holds no secrets).
- **RADIUS_Server**: The FreeRADIUS server that receives RADIUS Access-Requests from the AP and validates voucher credentials.
- **Voucher**: A unique, alphanumeric code generated by the system and given to a guest to authenticate onto the guest WiFi network.
- **Voucher_API**: The FastAPI REST API that manages voucher lifecycle (creation, validation, expiry, revocation) and serves the Admin Interface.
- **Database**: The PostgreSQL database that stores voucher records, audit logs, and admin credentials.
- **rlm_rest**: The FreeRADIUS module that enables FreeRADIUS to call an HTTP REST endpoint (the Voucher_API) to validate credentials.
- **rlm_sql**: The FreeRADIUS module that enables FreeRADIUS to query the Database directly via SQL to validate credentials.
- **Activation_Mode**: The policy that determines when a Voucher's expiry clock starts — either at creation time (pre-activated) or at first successful use (use-activated).
- **Consumed**: The state of a Voucher after it has been successfully authenticated for the first time. A Consumed voucher MUST be rejected on all subsequent authentication attempts.
- **Revoked**: The state of a Voucher that an Admin has manually invalidated before it was used or expired.
- **Walled_Garden**: A list of IP addresses or hostnames that the AP permits guests to reach before they are authenticated.
- **Audit_Log**: A time-stamped record of every authentication attempt, including outcome, voucher code, and client MAC address.
- **Voucher_API_Host**: The hostname or IP address of the server on which the Voucher_API is deployed. This value must be added to the AP's walled garden and must be set in the environment configuration.

## Requirements

### Requirement 1: Voucher Code Generation

**User Story:** As an Admin, I want to generate unique voucher codes with configurable expiry durations, so that I can distribute time-limited guest WiFi access to guests.

#### Acceptance Criteria

1. THE Voucher_API SHALL generate Vouchers whose codes are cryptographically random 12-character strings composed only of uppercase letters (A–Z) and digits (0–9), with no ambiguous characters (O, 0, I, 1).
2. WHEN an Admin submits a single-voucher generation request, THE Voucher_API SHALL create exactly one Voucher and return its code.
3. WHEN an Admin submits a batch generation request specifying a quantity, IF the quantity is less than 1 or greater than 500, THEN THE Voucher_API SHALL return an HTTP 400 error identifying the quantity constraint violation without creating any Vouchers; otherwise THE Voucher_API SHALL create the exact number of Vouchers specified and return all generated codes.
4. WHEN an Admin submits a generation request with a preset expiry duration, THE Voucher_API SHALL record the selected duration against each generated Voucher; supported preset durations are: 1 hour, 4 hours, 8 hours, 24 hours, 7 days, and 30 days.
5. WHEN an Admin submits a generation request with a custom expiry duration in whole minutes, IF the value is less than 1 or greater than 43200, THEN THE Voucher_API SHALL return an HTTP 400 error identifying the duration constraint violation without creating any Vouchers; otherwise THE Voucher_API SHALL record that custom duration against each generated Voucher.
6. THE Voucher_API SHALL store each generated Voucher in the Database with status `unused`, the configured expiry duration, and the Activation_Mode.
7. WHEN an Admin submits a generation request without specifying an Activation_Mode, THE Voucher_API SHALL default the Activation_Mode to `use-activated`.
8. IF a generated voucher code collides with an existing code in the Database, THEN THE Voucher_API SHALL regenerate that code up to 5 times; IF a unique code is not obtained after 5 attempts, THEN THE Voucher_API SHALL return an HTTP 500 error for that voucher without persisting it.
9. WHEN an Admin submits a generation request, IF an Activation_Mode value other than `use-activated` or `pre-activated` is provided, THEN THE Voucher_API SHALL return an HTTP 400 error identifying the invalid Activation_Mode value.

### Requirement 2: Voucher Validation via FreeRADIUS

**User Story:** As a guest user, I want to enter a voucher code on the captive portal so that I can gain authenticated access to the guest WiFi network.

#### Acceptance Criteria

1. WHEN FreeRADIUS receives a RADIUS Access-Request where both the `User-Name` and `User-Password` attributes equal the same Voucher code, THE RADIUS_Server SHALL query the Voucher_API or the Database to determine the Voucher's validity.
2. IF the queried Voucher exists in the Database, has status `unused`, and has an expiry timestamp that is later than the current server time at the moment of the request, THEN THE RADIUS_Server SHALL return a RADIUS Access-Accept to the AP.
3. IF the queried Voucher does not exist in the Database, THE RADIUS_Server SHALL return a RADIUS Access-Reject to the AP.
4. IF the queried Voucher has status `consumed`, THE RADIUS_Server SHALL return a RADIUS Access-Reject to the AP.
5. IF the queried Voucher has status `revoked`, THE RADIUS_Server SHALL return a RADIUS Access-Reject to the AP.
6. IF the queried Voucher has expired based on its recorded expiry time, THE RADIUS_Server SHALL return a RADIUS Access-Reject to the AP.
7. IF the Voucher_API or Database is unreachable or does not respond within 5 seconds, THEN THE RADIUS_Server SHALL return a RADIUS Access-Reject to the AP to prevent fail-open access.
8. WHEN the Voucher_API integration method is `rlm_rest`, THE Voucher_API SHALL expose a validation endpoint that FreeRADIUS can call via HTTP POST, and the endpoint SHALL return a response containing an explicit accept or reject indicator.
9. WHERE the integration method is `rlm_sql`, THE Database SHALL contain a view or table that exposes at minimum the voucher code, its status, and its expiry timestamp, such that rlm_sql can determine Voucher validity using a single SQL query.

### Requirement 3: Expiry Enforcement

**User Story:** As a system operator, I want voucher codes to expire automatically based on a configurable policy, so that guest access is time-limited without manual intervention.

#### Acceptance Criteria

1. IF a Voucher's Activation_Mode is `pre-activated`, THEN THE Voucher_API SHALL set the Voucher's expiry timestamp to the creation timestamp plus the configured expiry duration at the moment of generation, where the configured expiry duration is a value between 1 minute and 365 days inclusive.
2. IF a Voucher's Activation_Mode is `use-activated`, WHEN the Voucher is successfully authenticated for the first time, THE Voucher_API SHALL set the Voucher's expiry timestamp to the first-use timestamp plus the configured expiry duration, where the configured expiry duration is a value between 1 minute and 365 days inclusive.
3. WHILE a `use-activated` Voucher has not yet been used, THE Voucher_API SHALL treat the Voucher as not-yet-started and SHALL NOT reject it solely on the basis of elapsed time since creation.
4. IF the current UTC timestamp is greater than a Voucher's recorded expiry timestamp, THEN THE Voucher_API SHALL treat the Voucher as expired and SHALL return a rejection result that indicates the Voucher is expired as the reason for rejection.
5. THE Voucher_API SHALL store all timestamps in UTC and SHALL use UTC for all expiry comparisons.
6. IF the configured expiry duration is absent or outside the range of 1 minute to 365 days inclusive, THEN THE Voucher_API SHALL reject the generation request and return an error indicating that the expiry duration configuration is invalid, without creating or persisting any Voucher.

### Requirement 4: Single-Use Enforcement (Prevent Reuse)

**User Story:** As a system operator, I want each voucher to be usable only once, so that guests cannot share codes to gain repeated or concurrent access.

#### Acceptance Criteria

1. WHEN a Voucher is successfully authenticated, THE Voucher_API SHALL update the Voucher's status to `consumed` and record the consumption timestamp before returning an Access-Accept result.
2. IF a validation request is received for a Voucher with status `consumed`, THEN THE Voucher_API SHALL return a rejection result indicating the Voucher has already been used, regardless of the Voucher's expiry timestamp.
3. THE Voucher_API SHALL guarantee that a Voucher's status check and status update to `consumed` are performed as a single indivisible operation, such that no two concurrent validation requests for the same Voucher can both observe the status as unused.
4. IF two or more validation requests for the same unused Voucher are received before any one of them completes its status update, THEN THE Voucher_API SHALL ensure exactly one request receives an Access-Accept result and all remaining requests receive a rejection result indicating the Voucher has already been used.

---

### Requirement 5: Voucher Revocation

**User Story:** As an Admin, I want to revoke a voucher before it is used or while it is active, so that I can immediately terminate guest access for lost, stolen, or incorrectly issued codes.

#### Acceptance Criteria

1. WHEN an Admin submits a revocation request for a Voucher code with status `unused`, THE Voucher_API SHALL set the Voucher's status to `revoked`, record the revocation timestamp in UTC, and return a success response confirming the revocation.
2. IF a validation request is received for a Voucher with status `revoked`, THEN THE Voucher_API SHALL return a rejection response indicating the Voucher has been revoked.
3. IF a revocation request is submitted for a Voucher code that does not exist in the Database, THE Voucher_API SHALL return a 404 error response.
4. IF a revocation request is submitted for a Voucher that already has status `consumed` or `revoked`, THE Voucher_API SHALL return a 409 conflict error response indicating the current status.

---

### Requirement 6: Admin Interface

**User Story:** As an Admin, I want a web-based management interface, so that I can generate, view, search, and revoke vouchers without writing database queries or API calls manually.

#### Acceptance Criteria

1. IF an unauthenticated request is made to any Admin_Interface page route, THEN THE Admin_Interface SHALL redirect the request to the login page.
2. IF an unauthenticated request is made to any Admin_Interface API endpoint, THEN THE Voucher_API SHALL return an HTTP 401 response.
3. WHEN an Admin submits login credentials, IF the username or password is incorrect, THEN THE Admin_Interface SHALL display an error message indicating that the credentials are invalid without specifying which field is wrong.
4. WHEN an Admin navigates to the Voucher list, THE Admin_Interface SHALL display a paginated list of all Vouchers with a fixed page size of 25 items per page, showing: code, status, Activation_Mode, expiry duration, expiry timestamp (if set), creation timestamp, and first-use timestamp (if applicable).
5. WHEN an Admin applies a status filter, THE Admin_Interface SHALL update the Voucher list to show only Vouchers matching the selected status (`unused`, `consumed`, `revoked`, or `expired`).
6. THE Admin_Interface SHALL provide a form for generating a single Voucher or a batch of Vouchers, with fields for quantity (1–500), expiry duration (minimum 1 minute, maximum 365 days), and Activation_Mode.
7. WHEN an Admin confirms a revocation action on a Voucher with `unused` status, THE Admin_Interface SHALL submit the revocation request and display a confirmation message indicating the Voucher has been revoked.
8. IF an Admin attempts to revoke a Voucher whose status is `consumed`, `revoked`, or `expired`, THEN THE Admin_Interface SHALL display an error message indicating that the Voucher cannot be revoked in its current status, and the Voucher status SHALL remain unchanged.
9. WHEN a batch generation action completes successfully, THE Admin_Interface SHALL display all generated codes and provide an option to copy them to the clipboard or download them as a plain-text file.
10. WHEN an Admin logs out, THE Voucher_API SHALL invalidate the Admin's session so that subsequent requests using the same session token are rejected.
11. WHILE an Admin session is active with no requests made for 60 consecutive minutes, THE Voucher_API SHALL invalidate the session and THE Admin_Interface SHALL redirect the Admin to the login page on the next request.
12. THE Admin_Interface SHALL be served exclusively over HTTPS in all production deployment environments.

### Requirement 7: Audit Logging

**User Story:** As a system operator, I want all authentication attempts to be logged with relevant metadata, so that I can audit guest access, detect abuse, and troubleshoot failures.

#### Acceptance Criteria

1. WHEN a validation request is received by the Voucher_API, THE Voucher_API SHALL write an Audit_Log entry containing: the UTC timestamp, the voucher code as submitted, the client MAC address, the outcome (`accepted` or `rejected`), and the rejection reason when the outcome is `rejected` or a null value when the outcome is `accepted`.
2. THE Voucher_API SHALL write the Audit_Log entry regardless of whether the validation outcome is accepted or rejected.
3. WHEN an Admin views the Audit_Log page, THE Admin_Interface SHALL display Audit_Log entries in a reverse-chronological paginated list of 50 entries per page, showing the UTC timestamp, voucher code, MAC address, and outcome for each entry.
4. WHEN an Admin applies a filter on the Audit_Log page, THE Admin_Interface SHALL return only the Audit_Log entries matching all supplied filter criteria — voucher code (exact match), MAC address (exact match), outcome (`accepted` or `rejected`), or date range (start date inclusive, end date inclusive, matched against the UTC timestamp) — within 3 seconds.
5. IF the Audit_Log write fails due to a database error, THE Voucher_API SHALL still return the validation result to the caller and SHALL write an entry to the application log containing the UTC timestamp, the voucher code, the client MAC address, and an error message indicating the nature of the database failure.

### Requirement 8: Walled Garden Configuration

**User Story:** As a system operator, I want the Aruba AP's walled garden to permit access to the required hostnames before authentication, so that guests can reach the captive portal and the voucher validation backend without being blocked.

#### Acceptance Criteria

1. WHILE a guest device is unauthenticated, THE AP's walled garden configuration SHALL permit HTTP traffic (TCP port 80) to the Voucher_API_Host so that guests can reach the validation endpoint before authentication.
2. WHILE a guest device is unauthenticated, THE AP's walled garden configuration SHALL permit HTTP (TCP port 80) and HTTPS (TCP port 443) traffic to the domain `christianricv-tech.github.io` so that guests can load the Captive_Portal page before authentication.
3. WHILE a guest device is unauthenticated, THE AP's walled garden configuration SHALL permit HTTP (TCP port 80) and HTTPS (TCP port 443) traffic to `securelogin.arubanetworks.com` so that the portal can submit credentials to the Aruba authentication endpoint.
4. WHERE the Voucher_API is served over HTTPS, THE AP's walled garden configuration SHALL permit HTTPS traffic (TCP port 443) to the Voucher_API_Host in addition to HTTP traffic (TCP port 80).

---

### Requirement 9: Aruba External Captive Portal Compatibility

**User Story:** As a system operator, I want the backend to remain fully compatible with the verified Aruba InstantOS 8.11 external captive portal authentication flow, so that the AP can authenticate guests without custom firmware or unsupported modifications.

#### Acceptance Criteria

1. THE Voucher_API SHALL NOT require any modification to the Captive_Portal hosted at `https://christianricv-tech.github.io/WIFI-Guest/`.
2. WHEN a guest submits credentials via the Captive_Portal, the Aruba_AP SHALL direct the authentication request to `https://securelogin.arubanetworks.com/swarm.cgi` (or the value of the `switchip` parameter) using the form fields `cmd=authenticate`, `user=<voucher_code>`, and `password=<voucher_code>`; THE Voucher_API SHALL NOT intercept or modify this request flow.
3. THE RADIUS_Server SHALL accept an authentication request and return a RADIUS Access-Accept response when the RADIUS `User-Name` attribute and the RADIUS `User-Password` attribute both equal a valid, unused Voucher_Code using case-insensitive comparison, as this is the credential format produced by the Aruba swarm.cgi endpoint.
4. IF the RADIUS `User-Name` and `User-Password` attributes do not match a valid, unused Voucher_Code, THEN THE RADIUS_Server SHALL return a RADIUS Access-Reject response.
5. THE Voucher_API SHALL expose its validation endpoint at a URL path that shares no prefix segments with `/swarm.cgi`, ensuring no routing ambiguity between the Voucher_API and the `securelogin.arubanetworks.com` authentication path.

### Requirement 10: FreeRADIUS Integration Options

**User Story:** As a developer, I want the system to support both the `rlm_rest` and `rlm_sql` FreeRADIUS integration methods, so that I can choose the approach that best fits my deployment environment.

#### Acceptance Criteria

1. WHERE the `rlm_rest` integration method is selected, THE Voucher_API SHALL expose a dedicated RADIUS validation endpoint that accepts an HTTP POST request containing the voucher code and returns a response with a result field whose value is either `accept` or `reject`.
2. WHERE the `rlm_rest` integration method is selected, THE RADIUS_Server's `rlm_rest` module SHALL be configured to call the Voucher_API validation endpoint and map a result field value of `accept` to a RADIUS Access-Accept and a result field value of `reject` to a RADIUS Access-Reject.
3. WHERE the `rlm_sql` integration method is selected, THE Database SHALL expose a query mechanism (view or stored procedure) that returns at minimum the voucher code, password hash, and a validity flag indicating whether the voucher is unused and non-expired, such that the RADIUS_Server's `rlm_sql` module can determine whether a given username/password pair corresponds to a valid Voucher.
4. WHERE the `rlm_sql` integration method is selected, THE Database query used by `rlm_sql` SHALL NOT update Voucher status.
5. WHERE the `rlm_sql` integration method is selected, THE Voucher_API SHALL expose a post-authentication endpoint that the RADIUS_Server's post-auth handler calls after a successful Access-Accept, marking the corresponding Voucher as `consumed`.
6. THE system documentation SHALL describe, for each integration method, the complete sequence of configuration steps required to connect FreeRADIUS to the Voucher system on both a Windows development machine and a Linux VPS, covering all components that must be modified.

### Requirement 11: Data Integrity and Security

**User Story:** As a system operator, I want the backend to enforce data integrity and protect sensitive credentials, so that the voucher system cannot be bypassed through common web vulnerabilities or database manipulation.

#### Acceptance Criteria

1. THE Voucher_API SHALL use parameterized queries or an ORM for all Database interactions to prevent SQL injection.
2. THE Voucher_API SHALL store Admin passwords as salted cryptographic hashes using bcrypt or an equivalent password hashing algorithm with a minimum cost factor of 10; plaintext passwords SHALL NOT be stored in the Database.
3. THE Voucher_API SHALL validate all inputs from API requests against defined schemas and SHALL return HTTP 422 with an error response identifying the invalid field name and the reason for rejection for any request that fails schema validation.
4. WHILE the Voucher_API is running in production, THE Voucher_API SHALL serve all traffic over HTTPS using TLS 1.2 or higher.
5. IF a client sends a request over plain HTTP while the Voucher_API is running in production, THEN THE Voucher_API SHALL reject the request and return an error response indicating that HTTPS is required.
6. THE Voucher_API SHALL enforce rate limiting on the RADIUS validation endpoint to reject more than 60 requests within a fixed 60-second window from a single IP address, returning HTTP 429 for excess requests.

---

### Requirement 12: Deployment and Environment Configuration

**User Story:** As a beginner developer on Windows, I want clear environment configuration for both development and production, so that I can run the system locally and eventually deploy it to a Linux VPS without confusion.

#### Acceptance Criteria

1. THE Voucher_API SHALL read all environment-specific configuration values — including database URL, admin username, admin password, JWT secret key, and FreeRADIUS shared secret — from environment variables or a `.env` file, and SHALL NOT hard-code these values in source code.
2. IF the Voucher_API starts and any required environment variable (database URL, admin username, admin password, JWT secret key, or FreeRADIUS shared secret) is absent or empty, THEN THE Voucher_API SHALL exit immediately with an error message identifying each missing variable by name, and SHALL NOT proceed to serve requests.
3. THE Voucher_API SHALL include a `requirements.txt` file listing all Python dependencies with exact pinned versions (e.g., `package==1.2.3`), such that running `pip install -r requirements.txt` produces a reproducible installation.
4. THE Voucher_API SHALL include Alembic migration scripts so that the database schema can be created from scratch and incrementally updated by running the Alembic upgrade command, with each migration applied in sequence without manual SQL intervention.
5. IF an Alembic migration command fails, THEN THE Voucher_API SHALL leave the database at its last successfully applied migration version and SHALL NOT apply partial changes.
6. THE system SHALL include a README that provides sequential, numbered steps covering: installing Python dependencies on Windows, configuring a PostgreSQL database, configuring FreeRADIUS for both the rlm_rest and rlm_sql integration methods, running the Voucher_API locally, and deploying the system to a Linux VPS.
7. WHEN the `APP_ENV` environment variable is set to `development`, THE Voucher_API SHALL accept HTTP connections on a configurable port without requiring a TLS certificate, to simplify local testing.
